## Быстрый запуск

Установить Docker Desktop (Windows/macOS) либо Docker Engine с Compose (Linux), включить Docker. Из каталога проекта:

```sh
python3 scripts/setup.py
docker compose up -d --build --wait
docker compose ps
```

На Windows первая команда может выглядеть как `py -3 scripts/setup.py`. Остальные Docker-команды одинаковы. Python нужен для вспомогательных сценариев, сами сервисы запускаются в контейнерах.

Открыть http://localhost:8080. Prometheus: http://localhost:9090.

| Роль | Логин | Пароль учебного стенда |
| --- | --- | --- |
| Администратор | admin | DemoAdmin-2026! |
| Мастер | master | DemoMaster-2026! |
| Наблюдатель | viewer | DemoView-2026! |

Это демонстрационные значения. Для внешнего размещения задать собственные ADMIN_PASSWORD, MASTER_PASSWORD, VIEWER_PASSWORD до первого запуска. Изменение .env после создания базы не меняет пароль уже существующего пользователя. Пароль базы и ключ сессии генератор создаёт случайно. .env сохраняется локально и не входит в репозиторий.

## Возможности

Реестр заказов, поиск, фильтр по статусу, создание и изменение, ограниченное удаление плановых записей, назначение оборудования, учёт выпуска, проверка версии при одновременном изменении, аудит и CSV. Интерфейс и сообщения на русском языке. В начальном наборе 6 заказов и 4 единицы оборудования. Даты заказов рассчитываются относительно дня первой инициализации.

Переходы: planned -> in_progress -> completed. Из planned и in_progress доступна отмена. Завершение требует полного выпуска. Новые заказы всегда planned с выпуском 0. Закрытые заказы не редактируются. Перевод в производство запрещён, если оборудование на обслуживании.

## Шесть сервисов

| Сервис | Назначение | Сети |
| --- | --- | --- |
| frontend | Nginx, статический интерфейс, прокси | edge |
| api | Flask + Gunicorn, права и бизнес-правила | edge, backend, observability |
| db | PostgreSQL и том pgdata | backend |
| redis | Восстанавливаемый кэш и heartbeat | backend |
| worker | Обновление сводки каждые 5 секунд | backend |
| monitoring | Prometheus, опрос /metrics | observability |

В Compose работают 6 контейнеров. В Swarm 6 сервисов создают 8 задач: frontend и api имеют по 2 реплики. База и мониторинг закреплены за узлом хранения. PostgreSQL и Redis не публикуют порт на хосте.

## Два узла Docker Swarm

Изолированный лабораторный стенд использует два Docker-in-Docker контейнера. Для него требуется разрешённый privileged-режим Docker и достаточное место для копий образов. Основной Docker Engine хоста не переводится в Swarm. Сначала собрать и запустить обычный Compose-стенд, затем:

```sh
python3 scripts/swarm_lab.py
python3 scripts/smoke.py http://localhost:18080
docker compose -f swarm/lab.compose.yml exec manager docker node ls
docker compose -f swarm/lab.compose.yml exec manager docker service ls
```

При повторном запуске узлы и существующие секреты сохраняются. Скрипт передаёт образы потоком docker save/load. Имена узлов назначает Docker; они могут отличаться от записанных в отчёте. Секреты для лаборатории берутся из локального .env.

Остановка лаборатории без удаления томов:

```sh
docker compose -f swarm/lab.compose.yml stop
```

Привилегированные DinD-контейнеры используются для обучения. В облаке нужны обычные Linux-узлы с Docker Engine. Единственный manager и единственная PostgreSQL не дают полной отказоустойчивости. Два узла находятся на одном физическом компьютере и не моделируют независимость серверов.

## Наблюдение и резервирование

```sh
docker compose logs --tail=50
docker compose restart api
sh scripts/backup.sh
docker compose down
```

Обычная остановка сохраняет тома. Резервные копии создаются в backups/. На Windows использовать Git Bash/WSL либо вызвать `docker compose exec -T db pg_dump -U production -d production` и сохранить stdout без изменения кодировки.

Проверка копии на отдельной базе:

```sh
docker compose exec -T db createdb -U production production_restore
docker compose exec -T db psql -U production -d production_restore < backups/ИМЯ_КОПИИ.sql
docker compose exec -T db psql -U production -d production_restore -c 'SELECT count(*) FROM orders;'
```

Последняя команда сравнивается с числом заказов на момент создания копии. Восстановление поверх действующей базы требует отдельного планирования. Том PostgreSQL не является резервной копией.

## CI/CD и облачный сервер

В `.github/workflows/ci.yml`: тесты, Compose, smoke; после успеха основной ветви — публикация API и frontend в GHCR с тегом SHA. В `deploy.yml`: ручной запуск конкретного SHA, передача конфигурации по SSH, `docker stack deploy` и ожидание требуемого числа реплик.

Для первого облачного запуска:

1. Подготовить два Linux-сервера с Docker и Python, связанными доверенной сетью. Открыть между ними TCP 2377, TCP/UDP 7946 и UDP 4789. Для шифрованного overlay учитывать поддержку ESP. Не открывать служебные порты всему Интернету.
2. На первом узле выполнить `docker swarm init --advertise-addr АДРЕС_MANAGER`, второй присоединить командой join-token. Назначить первому узлу метку: `docker node update --label-add production_data=true ИМЯ_УЗЛА`.
3. Создать пять секретов Swarm: db_password, session_key, admin_password, master_password, viewer_password. Использовать собственные значения и передавать через stdin `docker secret create ИМЯ -`. Не копировать учебные пароли на внешний сервер.
4. Обеспечить право обоих узлов читать образы из GHCR. Для закрытого реестра предварительно выполнить docker login на manager и передавать авторизацию при развёртывании.
5. Установить внешний прокси с HTTPS и доменом. Проксировать запросы на manager:8080, ограничить этот порт доверенным прокси. В конфигурации выпуска COOKIE_SECURE=1.
6. В репозитории задать GitHub environment `production` и секреты CLOUD_HOST, CLOUD_USER, CLOUD_SSH_KEY, CLOUD_KNOWN_HOSTS. SSH-пользователь должен иметь необходимые права Docker. В CLOUD_KNOWN_HOSTS внести заранее проверенный ключ сервера.
7. Выполнить успешный CI в основной ветви, затем запустить Deploy с соответствующим полным SHA коммита. После сходимости отдельно проверить пользовательский сценарий через HTTPS-домен.

Конфигурации внешнего CI и облачной доставки подготовлены. Удалённый GitHub-конвейер, реестр и облачный сервер в ходе локальной проверки не подключались. Протоколы в evidence/ относятся к фактически выполненным локальным проверкам.

## Ограничения

Нет складского учёта, спецификаций, подключения станков, миграций схемы и резервной PostgreSQL. Сводка допускает небольшое отставание от операций. Метрики собираются через виртуальное имя сервиса, а не отдельно с каждой реплики. Redis-ограничение попыток входа использует адрес соединения с API; за прокси оно не является полноценной защитой каждого внешнего клиента. Для промышленной эксплуатации нужны нагрузочные проверки, аудит безопасности и отдельный план резервирования.
